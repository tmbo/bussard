Write a value to a KNX group address (GroupValueWrite) on the PHYSICAL bus. This has real-world effects: lights toggle, blinds and actuators MOVE, setpoints change. Only available when the server was started with --allow-writes. The value is human-typed (e.g. on/off, up/down, 75%, 21.5, a scene number, or an HVAC mode name) and is interpreted against the group address's DPT (override with `dpt`). Scene numbers (17.001, 18.001, 1.022) count from 1 as ETS and Home Assistant show them (KNX 03_07_02 §3.19 NOTE 9): `scene 3` sends the field 2, `raw 2` sends the field directly; reads show both, `scene 3 (raw 2)`. Relative dimming/blind steps (3.007, 3.008) take a direction and a step size: `increase 25%`, `down 50%`, `up`, `break`. Forced operation (2.x) takes `control on` (the 1.x word, e.g. `control down` on 2.008) or `release`. Scaled sub-types take the scaled value, never the raw count: 8.010 `50 %`, 7.003/7.004/8.003/8.004 `1.5 s`, 13.002 `1.5 m3/h`. Rate-limited (minimum 250ms between bus operations). Protected group addresses (safety-critical objects such as a wind alarm or central functions) are REFUSED outright — there is no override via MCP. When you are uncertain whether a write is safe or intended, ASK THE HUMAN before calling this tool. ok: true means only that the interface acknowledged the telegram (L_Data.con, the `result` field): KNX reports no application-level result, so never tell the human the device confirmed or executed it. On a secured (KNX Data Secure) GA the devices accept the telegram only if their security individual address table admits the tunnel address: a write the evidence says they would discard is refused (`refused: true`, with a `hint` on admitting the tunnel addresses). Without evidence the server first reads the devices' table (PID 54) once and records it; a write still sent without evidence carries `admission: unknown` and a `note` to pass on.
