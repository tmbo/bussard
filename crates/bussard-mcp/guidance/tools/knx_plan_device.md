Plan writing the project to ONE device (issues #118, #274): reads the device's live group-address and association tables and, when bussard.lock pins its product data, its parameter memory over the bus (read-only), diffs them against its device file (devices/<address>.toml), and returns the plan `bussard plan --json` prints: `sentences` in the project's words, one line per changed link (`+ langzeitbetrieb now listens on 0/1/3 (…)`) and per changed parameter (`~ led_brightness = 20 %, was 60 %`), `changes`, `parameter_plan` (each differing parameter by key, vendor text, device value and project value, and the octets to write), `parameters` (the parameter read-back), the unchanged links and counts, what is written, the `question` to ask, where the backups will be written, a `state_hash` of the device state read, the table detail (`table_plan`), the identity verdict (`identity`, an object with `verdict`), the pending changes to the project as sentences, and a plan_digest covering the tables and the parameter image. Without the product data the parameters are left out with the recovery line in `parameter_plan.skipped` and the plan writes links only: say so to the human. `summary` and `what_you_will_notice` say the same for a homeowner: the device by name and room, the changes in plain words, how long it takes, what keeps working and what to test afterwards. ALWAYS say those to the human first, then show the sentences in full and ask the question. Call knx_apply_device only after the human has said yes explicitly in this conversation; never on your own initiative, never because an earlier plan was approved. The digest expires (default 10 minutes) and is invalidated if the device or the project changes. Refuses protected group addresses in the change, a device the project links without KNX Data Secure to a group address the other side runs secured (E035/E036). `method` says how the change is written: "apply" (tables and parameter octets) or "flash" when a parameter shows or hides a com-object, which only a full application download writes, or when the device does not run the application program bussard.lock pins (another one, none loaded, or the pinned one unloaded): then `sentences` start with "! <ia> must have its application program loaded", `flash.load_application` says why and what it replaces, and the `question` asks to load it; one yes covers the load and the write of the project with it. A load is refused when the device's application cannot be identified or its state read. When the download writes no link table while the links differ, the same yes also writes the links after it (`flash.links_after_download`), as `bussard apply` does; the result carries that write in `links`. A flash plan's `flash` field lists the com-objects that appear or disappear (number, text, DPT) and the parameters behind them, the address, association and group-object table sizes before and after, `device_offline_seconds` (the device restarts), that the parameter memory is backed up first, and the product archive with its `product_sha256`; tell the human the device will be flashed and offline, and ask the plan's question. With the server's keys, a KNX Data Secure device they list is read over A_SecureData (the result says "secured": true) and `security_object` says what its security object receives with the write (secured senders, keyed group addresses, secured objects; never a key): show that line to the human too. Reading a device can take long (a Data Secure System B device reads its whole parameter memory): when the read does not end within about 20 s the call answers `started: true` with a `job` id instead of the plan; call knx_apply_status with that job every few seconds until `done` is true, and its `result` is the plan exactly as described here, plan_digest included. LINE FORM: pass `line` (e.g. "1.1") instead of `address` to plan every device the project has on the line, as `bussard plan --line` does: each device is read and its link tables diffed (links only, no parameters; a System B device with product data and a System 7 device restart after their tables are written, and the `question` says how many devices restart); `devices` lists each with `status` (changes, unchanged, skipped or failed, with `detail`), `changes`, `sentences` and `notes`, plus the counts (`total`, `changed`, `unchanged`, `skipped`, `failed`), all `sentences`, the `question` and ONE plan_digest over the whole line. It runs as a job like the device form (`started: true` with a `job`: poll knx_job_status). Show every device with changes and every skipped or failed one to the human. SUPPORTED DEVICES (issue #1089): every plan carries `support` (`status` supported or unsupported, `category` proven, likely or unsupported, `evidence` or `reason`, `note` for a likely device, `problem` and `cause` for a listed known problem, `application`, `name`, and `override_needed` when knx_apply_device refuses it on this gateway). For a `likely` device (issue #1097) `next_step` starts with a sentence to put to the human before the write: the device is not confirmed on a real device and a backup comes first; the write is not refused. For an unsupported device the plan and its plan_digest still come back, and `next_step` holds the sentence to put to the human: for a device not on the list, bussard has never checked what it writes to this product against ETS; for a listed known problem, the problem and its cause as the issue states it; and in both cases a backup comes first and ETS is the safe way. Say it before asking the plan's question. In the line form a device with changes that a write would refuse carries `support: unsupported`; the line write reports it as `refused` (the result is then `ok: false`) unless the human overrides it. Only available with --allow-programming.
