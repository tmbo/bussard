Write the planned change to ONE device on the PHYSICAL bus (issues #118, #274, #289): the group-address and association tables when a link changes, then the parameter octets that differ, with the engine `bussard apply` uses. Call this ONLY after you showed the human the plan from knx_plan_device and the human answered yes explicitly in this conversation. Pass the plan_digest from that plan, and its state_hash as plan_hash to refuse if the device changed since. Refuses unless the digest came from this server session within the plan lifetime and a fresh read of the device, with the current project, still matches it; if refused, plan again and ask again. The pre-flight (gates, digest, identity, backups of the tables and parameter memory) runs in this call; the write and its read-back run as a job in the server. When the write ends within about 20 s the reply is the full result with `started: false, done: true` (the verify outcome, `parameters` written, the backup paths); otherwise it is `started: true` with the `job` id: call knx_apply_status with that job until `done` is true, and knx_last_apply with the address recovers the result if a reply is lost. A pre-flight read that outlasts about 20 s (a Data Secure device) also answers `started: true`; if it then refuses, the job ends with `result.refused: true` and nothing written. One job at a time: a second call while a job (an apply or a plan) runs is refused with its id. Tell the human the outcome and the backup paths. A KNX Data Secure device the server's key store (or keyring) lists is written over A_SecureData, its security object reprogrammed with the tables, exactly as `bussard apply --keyring` does. A plan with `method: "flash"` runs the full application download `bussard flash --yes` writes, through the same service function (the parameter memory backed up first when it is readable, then the download, the restart, the independent read-back and the lock update) as the same job; call it only after the human said yes to flashing the device. When the plan loads the application (`flash.load_application`), the result carries `load_application` with `loaded`, and `ok` is true only when the read-back matches the project. LINE FORM: pass `line` and the plan_digest of knx_plan_device's line plan (instead of `address`) after the human's explicit yes to it, to write the line as `bussard apply --line` does: one job (poll knx_job_status) that writes each device with changes in address order, each backed up first and verified by an independent read-back; a device that fails is reported and the next one is tried, and a device whose fresh read no longer matches the plan is not written. Refused when the project's devices or links on the line changed since the plan, or the project has validation errors. The result lists per device `status` (applied, unchanged, skipped, failed), `verified`, `changes`, `sentences`, `backup` and `detail`; `ok` is true only when no device failed: report every failed device. SUPPORTED DEVICES (issue #1089): on a gateway that is not loopback, a device (an IP interface's KNXnet/IP parameter object included) whose application is not on bussard's list of supported devices is refused with `code: "unsupported_device"`, `support` and `override`; nothing is written and the plan_digest stays valid. Never decide this yourself: tell the human what the refusal says and ask whether to write anyway. Only after their explicit yes call again with the same plan_digest and `allow_unsupported: true`; the flag counts only with the digest of a plan that reported the device unsupported. The result of such a write carries `support: "forced"` (otherwise `supported`, or `unsupported` on a loopback gateway, which never refuses). When the chat app shows bussard's own questions (elicitation), bussard asks the human itself before writing such a device and `allow_unsupported` does not count; a no is a refusal with nothing written (issue #1093). Only available with --allow-programming.
