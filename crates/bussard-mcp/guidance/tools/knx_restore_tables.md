Write a backup's group-address and association tables back onto ONE device on the PHYSICAL bus, as `bussard restore <backup> <address>` does (issue #717), in two calls. `backup` names a knx_backup_device run (its `backup` field) or a file under captures/backups/; omitted, the newest pre-write backup an apply kept of the device. Without plan_digest: reads the device (read-only) and returns the plan: `table_plan` (what is added and removed), `additions`, `removals`, the table sizes, `security_object` on a secured device, the `question` and a plan_digest; `noop: true` when the device already holds the backup's tables. Say the `summary`, show the plan to the human and ask the question. With the plan_digest (ONLY after the human's explicit yes in this conversation): re-reads the device, refuses if the device or the backup moved, records a history snapshot, backs up the current tables, writes them with knx_apply_device's engine and reads them back independently, as a job (`started: true` with a `job`: poll knx_apply_status; knx_last_apply recovers it). `verified` is true only when the read-back matches the backup. Only the link tables are written, never parameters. Refuses a backup of another device or mask, a backup outside captures/backups, and a change touching a protected group address. SUPPORTED DEVICES (issue #1089): the plan carries `support`. On a gateway that is not loopback, a device not on bussard's list of supported devices is refused with `code: "unsupported_device"`; nothing is written and the plan_digest stays valid. Only after the human's explicit yes to writing it anyway, call again with the same plan_digest and `allow_unsupported: true`; the result then says `support: "forced"`. When the chat app shows bussard's own questions (elicitation), bussard asks the human itself before writing such a device and `allow_unsupported` does not count; a no is a refusal with nothing written (issue #1093). Only available with --allow-programming.
