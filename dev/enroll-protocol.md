# Certificate enrolment protocol (v2)

How a KNX Secure device certificate (the 36-character FDSK label) gets from a
phone camera into `bussard.keys` without passing through the chat, the MCP
client, the hosted page's server or the relay in readable form. Design and
decision: #201 ("Certificate entry"); v2 hardening after the security review
of 2026-11-04: #796. Test vectors: `dev/enroll/vectors-v2.json` (synthetic
keys only), generated by `node dev/enroll/regen-vectors.mjs`. Every
implementation (Rust session and local relay, the web page, the hosted
relay) checks itself against those vectors.

v2 is not compatible with v1 and nothing negotiates: the link, the envelopes
and every label carry the version, and a side that sees another version
refuses it. What changed from v1: one phone per session, a slow session code,
connect, idle and maximum timeouts with a sliding relay expiry, the `hello`
and `refused` messages, a `reason` on `closed`, no device on an `invalid`
result, `https` relays only, and relay limits on long polls and session
creation.

## Parties

| party | runs | sees |
|---|---|---|
| bussard | `bussard keys enroll`, or the MCP tool `knx_enroll_certificates` | plaintext, writes the key store |
| page | static HTML/JS at `https://bussard.tmbo.dev/enroll/` (or served by bussard on localhost) | plaintext, in the phone's browser only |
| relay | a mailbox service (the hosted Worker at `https://bussard-relay.tmbo.dev`, the default, or bussard's in-process local relay) | ciphertext, session ids, timing, client IPs |
| chat / MCP client | the link and the results | the link (public key only), serials, addresses; never a key |

The page's JavaScript and the relay are trusted to be the project's. When a
session uses a page or relay other than the defaults (`--page`, `--relay` or
`[enroll]` in `bussard.toml`), bussard says so before it shows the link
(finding F13): a warning line in the CLI and a `warnings` entry in the MCP
result, naming the page or relay. Local mode (bussard serves both on the
loopback interface) is not a different page in that sense and gets no
warning.

## Flow

1. bussard generates a session: a 16-byte random session id `sid`, an X25519
   key pair `(b_sk, b_pk)` and a 32-byte random owner token. It creates the
   session on the relay (`PUT`, owner token as bearer).
2. bussard derives the session code (below) and shows the link, as text and
   as a terminal QR code, and the session code. Over MCP the tool returns
   the link and the session code.
3. The phone opens the link. The page generates its own X25519 key pair
   `(p_sk, p_pk)` for this session (or loads the one it kept, see
   "Reconnect"), derives the session key and the session code, shows the
   code, sends `hello` and opens the camera.
4. The first phone key whose message bussard can open owns the session (see
   "One phone per session"). Every other phone key is refused.
5. Each scanned or typed certificate is normalized and checked on the phone,
   then sent encrypted (`up`).
6. bussard long-polls `up`, decrypts, matches the serial against the model,
   stores the FDSK, and answers with a `result` (`down`, encrypted for that
   phone key). The page shows it per sticker.
7. The session ends when the phone sends `done`, bussard stops (the user
   ends it, or a timeout below runs out) or the relay expires it. bussard
   posts `closed` to the owning phone and deletes the session on the relay.

## Timeouts

bussard ends a session on whichever comes first:

| timeout | length | counted from |
|---|---|---|
| connect | 10 minutes | the session's creation, until a phone owns the session |
| idle | 15 minutes | the owning phone's last message (a certificate, or the `hello` keep-alive) |
| maximum | 4 hours | the session's creation |

The page sends `hello` when it opens and again whenever it has sent nothing
for 5 minutes while it is open, so an open page keeps the session alive and
a page that is closed, or a phone that is locked, lets it run idle. Messages
from a refused phone do not count.

The relay's expiry follows the same clock from its side (see "Relay API"):
15 minutes after the session's last write, never later than 4 hours after
its `PUT`. bussard enforces the timeouts itself; the relay's expiry is the
backstop for a bussard that ended without its `DELETE`.

The lengths are the owner's decision of 2026-11-04 (#796): 30 minutes from
creation (v1) was too short for a long list, and a phone that loses signal
for a moment must be able to come back (see "Reconnect").

## One phone per session

The first phone key whose `up` message opens under bussard's key owns the
session. From then on bussard processes only that key's messages:

- A message from another phone key that opens is refused: bussard does not
  process it (no certificate is stored, a `done` does not end the session),
  answers that key once with `refused`, and reports "another phone tried to
  join" loudly: a line in the CLI, and a count in the MCP session status.
  The refused page says the session belongs to another phone.
- A message that does not open (garbage, a wrong key, a tampered envelope)
  is dropped and counted, not reported per message.
- bussard answers at most 16 different refused keys; beyond that it only
  counts them, so a flood of keys cannot fill the `down` queue.

Anyone who learns the link (the chat, the MCP client, a shoulder) can
derive a session key and post messages that open. They still cannot read
anything another phone sends, and the session code shows whether the link
was altered. What they can do is race the real phone to own the session:
the real phone then shows "this session belongs to another phone" and
bussard reports a second phone, which tells the user to stop. In v1 any link
holder could add certificates to a running session (finding F3 of the
2026-11-04 review); v2 limits that to being the first phone, which the user
notices.

A link holder (and the relay) can also disrupt a session: fill a direction
to its message limit, or keep long polls busy. That is accepted; it costs
the user a new session, never a key.

## Reconnect

A phone that loses signal, switches networks or reloads the page comes
back as the same phone:

- The page keeps its phone key for the session in IndexedDB as a
  non-extractable WebCrypto `CryptoKey`, keyed by the session id, and deletes
  it when the session ends (`done`, `closed`, `refused`, or a `404` from the
  relay) or when it is older than 4 hours. The key never leaves WebCrypto;
  page script cannot read its bytes.
- After a reload it loads that key, reads `down` from `after=0` to rebuild
  its list of results, and numbers new certificates after the highest `id`
  it has seen or sent.
- A failed poll or post is retried with backoff (1 s doubling to 30 s), and
  the page shows "reconnecting" until a request succeeds, not an error. Only
  a `404` (the session is gone) or `closed: true` ends it.

bussard needs nothing for a reconnect: the phone key is the identity, and
the relay keeps every message until the session ends.

## Encoding

- All binary values in links, envelopes and JSON are base64url without padding.
- Link: `<page>#v=2&s=<sid>&k=<b_pk>&r=<relay base URL, percent-encoded>`.
  Everything after `#` stays in the browser; the page's server never sees it.
  `r` is omitted when the page and the relay share an origin (local mode).
- A relay URL must be `https`, or `http` on a loopback host (`localhost`,
  `127.0.0.0/8`, `[::1]`). bussard refuses any other relay before it creates
  a session (finding F9), and the page refuses such a link.

## Session code

Both sides show the session code (`fingerprint` in the code and in v1); a
mismatch means the link was altered on its way to the phone. It is
`XXXX-XXXX`, the uppercase hex of

```
PBKDF2-HMAC-SHA256(password   = b_pk (32 raw bytes),
                   salt       = ASCII "bussard-enroll-v2 session code" || sid (16 raw bytes),
                   iterations = 1 000 000,
                   dkLen      = 4)
```

WebCrypto computes it as `deriveBits({name: "PBKDF2", hash: "SHA-256", salt,
iterations}, importKey("raw", b_pk, "PBKDF2"), 32)`.

Why slow (finding F2): whoever can rewrite the link (the chat, the MCP
client) can put in their own `b_pk` and must then make its 32-bit code
match the one bussard shows. With v1's single SHA-256 that took about 2^31
hashes, under a second on one GPU, in real time. With 10^6 PBKDF2
iterations the same search costs about 2^31 x 10^6 HMAC iterations, about
three GPU-days at the roughly 9 x 10^9 PBKDF2-SHA256 iterations per second
of a current high-end GPU, and has to finish while the user looks at the
code.

The count was picked by measurement on 2026-11-04: Node 24's WebCrypto
(OpenSSL) on an Apple M1 Max derives 10^6 iterations in 125 to 130 ms. A
mid-range phone's WebCrypto runs PBKDF2 some 4 to 8 times slower than that
core, so about 0.5 to 1 s, once per page load; bussard derives it once per
session. No phone was measured; re-measure on one when the count is
revisited.

What it does not stop: the code is 32 bits (the owner kept the `XXXX-XXXX`
format, 2026-11-04), and the link rewriter also chooses `sid`, so a
precomputed table of key pairs per code is possible. Covering half the codes
costs about 0.7 x 2^32 x 10^6 iterations, some four GPU-days, once. The
slow derivation prices that table; a longer code would be the next step.

## Crypto

```
shared = X25519(p_sk, b_pk) = X25519(b_sk, p_pk)     reject all-zero
key    = HKDF-SHA256(salt = sid (16 raw bytes),
                     ikm  = shared,
                     info = "bussard-enroll-v2" || b_pk || p_pk,
                     L    = 32)
aad    = ASCII "bussard-enroll-v2/<dir>/<sid base64url>"   dir = up | down
c      = AES-256-GCM(key, nonce (12 random bytes), plaintext, aad)   tag appended
```

One key per (session, phone key). bussard can derive a key for any phone
key, which is how it opens and refuses a second phone. Nonces are random
per message.

Envelope (both directions, at most 4096 bytes serialized):

```json
{"v": 2, "pk": "<p_pk>", "n": "<nonce>", "c": "<ciphertext+tag>"}
```

`pk` is always the phone's key: it selects the key on bussard's side for `up`
and addresses the phone for `down`.

### Replays

Within a session, a replayed `up` envelope (by the relay, or by anyone who
copied it) is handled again and harmless: a certificate stores the same key
and answers `already_stored`, a `hello` refreshes the idle timer. A replayed
`done` ends the session early, which the relay could do anyway by dropping
messages. A replayed `down` envelope shows a result twice; the page keys
results by `id`. Across sessions a replay does not open: `sid` is in both
the HKDF salt and the AAD (finding F11).

## Messages (plaintext, UTF-8 JSON)

Up (page to bussard):

| type | fields |
|---|---|
| `hello` | none: the page is open (sent on open, and after 5 minutes without another message) |
| `certificate` | `id` (page-local counter, unique per phone key within the session), `text` (36 normalized characters) |
| `done` | none: the user finished on the phone |

Down (bussard to page):

| type | fields |
|---|---|
| `result` | `id` (echoes the certificate), `status`, `serial` (12 hex digits; absent when the label could not be decoded), optional `ia`, `name`, `message` |
| `refused` | none: this session belongs to another phone; nothing this phone sends is processed |
| `closed` | `stored` (count), `reason`: bussard ended the session; best effort, see below |

`status` is one of `stored` (matched to a device and saved), `unassigned`
(saved under its serial, no device in the model has it yet), `already_stored`
(the same FDSK is already in the store), `conflict` (the store holds a
different FDSK for this serial; nothing written), `invalid` (format or check
failed; the page should have caught it), `error` (`message` says why).

An `invalid` result never carries `ia` or `name` (finding F7): a label that
does not check must not tell its sender which device a serial belongs to.

`reason` is one of `done` (the phone sent `done`), `stopped` (the user ended
it on bussard's side), `idle_timeout`, `max_duration`. A page treats an
unknown `reason` as the end of the session all the same.

No down message ever carries an FDSK, a tool key or any other key.

bussard posts `closed` and then deletes the session, so a phone that polls
after the `DELETE` sees only `"closed": true` and never the `closed` message.
The page treats both as the end of the session and shows its own tally of
`result`s; `closed.stored` is a convenience, not the record.

## Relay API

JSON over HTTPS. CORS allows any origin on the phone-side endpoints
(`POST up`, `GET down`). Unknown or expired sessions answer `404`.

| method and path | auth | body / answer |
|---|---|---|
| `PUT /v1/sessions/{sid}` | owner | `{}` → `201`; `409` if it exists |
| `POST /v1/sessions/{sid}/up` | none | envelope → `202 {"seq": n}` |
| `GET /v1/sessions/{sid}/up?after=<seq>&wait=<s>` | owner | `{"messages": [{"seq": n, "body": envelope}], "closed": false}` |
| `POST /v1/sessions/{sid}/down` | owner | envelope → `202 {"seq": n}` |
| `GET /v1/sessions/{sid}/down?after=<seq>&wait=<s>` | none | same shape as `GET up` |
| `DELETE /v1/sessions/{sid}` | owner | `204`; later reads answer `{"messages": [], "closed": true}` until expiry |

- owner = `Authorization: Bearer <owner token>`, set by the `PUT`.
- `wait` is a long poll, at most 25 seconds; `after` defaults to 0 and
  `seq` starts at 1 per direction.
- The relay checks an envelope's shape (`v` is 2, `pk`, `n`, `c` base64url)
  and nothing else.
- Expiry slides: a session expires 15 minutes after its last write (the
  `PUT` and every accepted `POST`, in either direction), and never later
  than 4 hours after its `PUT`. Reads and `DELETE` do not move it. The relay
  keeps nothing after expiry.
- Limits: 500 messages per direction and 4096 bytes per envelope, `429`
  beyond them. 500 leaves room for a long list plus the `hello` keep-alives
  of 4 hours (at most 48).
- Long polls: at most 4 open per direction per session. A fifth makes the
  oldest open one answer at once with what it has (usually no messages), as
  if its wait had run out. A phone that reloaded, or bussard after a network
  change, is never locked out by its own stale polls.
- Session creation (hosted Worker only): at most 10 `PUT`s per client IP
  per minute, `429` beyond. bussard's local relay listens on loopback only
  and has no such limit.
- Owner token: the relay stores SHA-256 of the bearer string's UTF-8 bytes.

Status codes the cases in `services/enroll-relay/test/cases.json` pin (the
hosted Worker and bussard's local relay both pass them):

| situation | status |
|---|---|
| missing or wrong owner token | `401` |
| malformed `sid`, envelope, `after` or `wait` | `400` |
| `wait` above 25 | clamped to 25, not an error |
| unknown or expired session, including a long poll still open at expiry | `404` |
| `POST` after `DELETE` | `404` |
| `PUT` on a deleted session that has not expired | `409` |
| envelope over 4096 bytes, or a direction past 500 messages | `429` |
| a fifth long poll in one direction | `200` for it; the oldest open one answers at once |

Tests shorten the expiry through two settings (`SESSION_IDLE_SECONDS` and
`SESSION_MAX_SECONDS` in the Worker); they can only shorten, never
lengthen, the 15 minutes and 4 hours. The per-IP creation limit is
`CREATES_PER_IP_PER_MINUTE`; the shared cases do not cover it, because
bussard's local relay has none, so the Worker's own tests do.

Operational limits outside the code (a Cloudflare rate-limiting rule on the
dashboard, a billing alert) are the owner's and are not part of this
contract.

## Certificate text

36 characters, RFC 4648 base32 (`A-Z`, `2-7`), printed as six groups of six
separated by dashes. Decoded as a 180-bit big-endian number: the upper 176
bits are the serial number (6 bytes) then the FDSK (16 bytes), the lower
4 bits a check.

Normalization, identical on the page and in bussard: drop whitespace and
`-`, uppercase, map `0` to `O`, `1` to `I` and `8` to `B` (base32 has none of
them), then require exactly 36 characters of the alphabet.

The check is plain CRC-4 over the 22 bytes serial || FDSK: polynomial
x^4 + x + 1 (`0x3`), init 0, MSB first (input and output not reflected), no
final XOR, computed directly (not augmented with four zero bits):

```
c = 0
for byte in serial || fdsk:
    for bit in 7 down to 0:
        top = ((c >> 3) & 1) ^ ((byte >> bit) & 1)
        c = (c << 1) & 0xF
        if top: c ^= 0x3
```

Its value over the ASCII bytes `123456789` is `0xE`. This is not CRC-4/ITU
(the reflected variant). Confirmed on two real labels (#201, 2026-11-03). A
label whose check does not match is `invalid`, on the page and in bussard.

The label's QR code carries the same 36 characters without dashes (confirmed
on the same labels). The page still extracts the first 36-character base32
run (dashes allowed) from a QR payload.

## Vectors

`dev/enroll/vectors-v2.json` holds the session (both key pairs, `sid`, the
shared secret, the session key, the session code and its salt, the link),
the owning phone's messages (`hello`, two certificates with a `stored` and
an `invalid` result, `done`, `closed`), a second phone (`other_phone`) with
its `hello` and the `refused` answer, and the certificate vectors. Every
value is computed by `node dev/enroll/regen-vectors.mjs` from fixed
synthetic inputs with `node:crypto` alone; `--check` verifies the file is
current. Neither the page's code nor bussard's computes the vectors they
are checked against.

`dev/enroll/vectors-v1.json` is the frozen v1 set the implementations still
read until they move to v2 (#796); it goes then.
