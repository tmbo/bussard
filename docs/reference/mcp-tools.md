# MCP tools

What the `bussard mcp` server offers an assistant: its tiers, every tool, the bus connection, and the gates in front of the programming and Home Assistant tiers.

The server speaks the Model Context Protocol over stdio. Its flags and how to register it with a client are on [`bussard mcp`](commands/servers.md#bussard-mcp); why the tiers exist is in [The assistant](../explanation/assistant.md).

## Tiers

Four bus tiers, a Home Assistant tier, and a switch for the model edits:

| Tier | Flag | On the bus |
|---|---|---|
| Passive | `--passive` | Never transmits. The bus-touching read tools (`knx_read_group`, `knx_describe_device`) and `knx_bus_reconnect` are not registered, and `knx_audit` refuses `live: true`. `knx_bus_status` stays. |
| Read (default) | none | May send GroupValueReads, rate-limited. |
| Write | `--allow-writes` | Adds `knx_write_group` and `knx_run_tests`. |
| Programming | `--allow-programming` | Adds `knx_plan_device` and `knx_apply_device`, plus `knx_apply_status` and `knx_last_apply` for the apply job, which write one device's link tables and the parameter values that differ after a plan the human approved, and `knx_restore_parameters`, which replays a parameter backup the same way. Needs a loopback gateway or the real-gateway opt-in. Independent of `--allow-writes`; not available with `--passive`. |
| Home Assistant | `--allow-home-assistant` | Never touches the bus. Adds `knx_ha_status`, `knx_ha_plan`, `knx_ha_apply`, `knx_ha_automation_plan`, `knx_ha_automation_apply` and `knx_ha_automation_remove` when `bussard.toml` has a `[home_assistant]` table: read Home Assistant, write the KNX YAML it reads, and manage bussard's own automations, each write after a plan the human approved. Combines with every tier above. |
| No model edits | `--no-model-edits` | Withholds the six model-edit tools, `knx_scaffold_groups` and `knx_reserve_groups`. Orthogonal to the tiers above: they write the model's TOML files, never the bus, so they are registered in every tier by default. |

- Tool counts: 23 in `--passive`, 26 by default, 28 with `--allow-writes`. `--no-model-edits` takes eight away from each (15, 18 and 20). `--allow-programming` adds two to any non-passive tier. The Home Assistant tier adds six to any tier.
- Bus operations share one rate limiter: at least 250 ms between operations, at most two in flight.
- A group address marked `protected = true` is hard-refused by `knx_write_group` and `knx_run_tests`, with no MCP override. The assistant must ask a human, who can run `bussard write ... --force` from the CLI.
- A full application download (`flash` of a new application), `apply --line`, `adopt`, `replace` and `commission` are CLI-only.

## Model tools

The model tools (`knx_describe_change`, `knx_history`, the six that edit, `knx_scaffold_groups` and `knx_reserve_groups`) touch files under the model directory and nothing else. `knx_export_bundle` and `knx_diff_project` only read the model (the export writes one bundle file) and are registered in every tier, `--no-model-edits` included.

Every edit snapshots the model first, validates after, and returns the change as sentences for the assistant to quote to the human. An edit or `knx_undo` result carries `changes` (the sentences), `detail` (the same changes as JSON), `validation` and `next_step`:

- **`validation`** is `{ok, errors, error_count, new_warnings, warning_count}`. `errors` are the model's errors after the edit; `new_warnings` only the warnings the edit introduced (a warning counts as old when its code, location and message were there before), so an edit that adds none returns `[]`. Each list stops at 20 entries with a `note` giving the totals; `knx_validate` returns the full list.
- **Caps.** `changes` and `detail` stop at 50 entries (`knx_describe_change` at 200), protected ones first, with a `truncated` note naming the totals.
- **Parameter sentences** compare enum values by member: a device file's label and the code the model holds for it are no change. An enum value reads as its label with the code after it (`Funktion on Taster (1.1.7) is set to Kurzer und langer Tastendruck (5).`); `detail` keeps the values as the model holds them.

The model is not frozen at startup. The server re-reads the model directory when its files change, and immediately after one of its own edits, so a `protected = true` or a corrected `dpt` added to `groups.toml` mid-session is in force on the next tool call. A model that fails to parse is not swapped in; the server keeps the last good one and warns on stderr.

## What the server tells the assistant

Clients load tools lazily, so a tool description or a result string is often all the assistant knows at the moment of a call. Every string that depends on what the server may do is built from its active tiers:

- **Server instructions.** What the server does end to end at its tier, which tools push, and what still needs the CLI (`flash` of a new application, `adopt`, `replace`, `commission`; a parameter that shows or hides com-objects needs `bussard flash <ia>`) or ETS (the Secure activation of a fresh device, and any setting the product model does not expose). Parameters are edited with `knx_set_parameter` using the keys `knx_show_device` lists. To find a device that can provide a function, the assistant uses `knx_model_lookup` with the function's words and reads `knx_show_device` for the candidates.
- **`knx_get_device` versus `knx_show_device`.** The first is the configured state (the device file: links and stored parameters), the second what the device can do (every parameter the configuration shows, the inactive pages and channels with what enables them). Each description says so.
- **`next_step` after a model edit.** Names the devices the change touches. With `--allow-programming`, push with `knx_plan_device` for the device and `knx_apply_device` after an explicit yes; without it, restart with the flag, or run `bussard plan <ia>` and `bussard apply <ia>` at the CLI. Names, rooms and group-address metadata are stored in no device: nothing to push. With the Home Assistant tier on, an edit that touches a group address Home Assistant's KNX config uses adds a line naming `knx_ha_plan` and `knx_ha_apply`.
- **Tool descriptions** of the six edit tools name `knx_plan_device` and `knx_apply_device` as the push step and leave the tier-specific part to `next_step`.
- **`knx_project_summary`** carries `server` (`tiers`, `passive`, `writes`, `programming`, `model_edits`, `home_assistant`) and `capabilities`, one paragraph saying what the assistant may do here.
- **`knx_show_device`** carries `how_to_change` when unscoped: which tool edits the listed parameters and links, how they are pushed, and the parameter key grammar. Without a product model it says the parameters are not editable yet and what to run.

| `knx_model_lookup` | `query` (substring), `limit` (default 50, max 500) | Case-insensitive matches across GA names/addresses, device names/IAs, room names, com objects and channels, grouped by kind (`groups`, `devices`, `objects`, `channels`), plus `capabilities`. A channel matches on its vendor text, name or handle and lists its object numbers. `capabilities` searches what the installed devices could do: the parameter texts and enum choice texts of their product models, every word of the query in the page title, parameter text and choice text together (case and umlaut spelling do not matter: `Dämmerung` finds `daemmerung`). | `knx_show_device` | `address`, `channel` (optional; a handle, a page handle, or `device`), `toml` (optional), `inactive` (optional) | What [`bussard device`](commands/devices.md) shows, as JSON: what the device can do. With `channel` the response stays small: `blocks` and `inactive_channels` are one line each (handle, text, state, parameter and object counts), the scope keeps its full `inactive` detail, `inactive: true` adds the other inactive pages in full as `inactive_pages`, and `how_to_change` is left out (the tool description carries it). Files only. |
| `knx_recent_telegrams` | `limit` (default 50, max 1000), `ga` (GA or prefix), `source` (IA), `since` (RFC3339), all optional | Recent decoded telegrams, oldest first. With `--capture-db`, windows that predate the in-memory ring are topped up from the capture database. |

| `knx_scaffold_groups` | `plan` (JSON `{rooms: [{floor, room, functions}]}`), `scheme` (optional) | Writes `groups.toml` from a room and function list, returns the addresses added and the model's validation counts. Confirm the room list with the human first. |

With the server's keyring, a Data Secure device the keyring lists is read over KNX Data Secure (`secured: true`), and `security_object` says what its security object receives with the write: `summary` (the line `bussard apply --keyring` prints), `secure_senders`, `keyed_groups` and `secured_objects`, never a key. A group the model marks `secure` without a key in the keyring refuses the plan. When the device read does not end within the read wait (20 s from the start of the call; a Data Secure System B device reads its whole parameter memory), the call answers `started: true`, `done: false`, `kind: plan`, `job`, `address` and `next_step` instead; `knx_apply_status` with that job returns the plan as `result` once `done`, exactly as the inline answer, `plan_digest` included. A second call for the same device while its plan job runs returns the same job; a plan is refused while an apply runs, and an apply while a plan runs. Registered only with `--allow-programming`. |

## The bus connection

The server keeps one bus connection for its whole life and reconnects it on its own. A lost tunnel first re-establishes itself within `BUSSARD_TUNNEL_RECONNECT_SECS` (see [Environment](environment.md)). Then the connection is opened afresh, with a backoff of 1, 2, 4, 8, 16 and then 30 s between failed attempts. Every attempt is a new socket and a new KNXnet/IP Secure session; nothing of a failed attempt is reused.

While the bus is down, a bus tool is refused with the last error, for example:

```text
the bus to 192.0.2.10:3671 is not connected: socket error (192.0.2.10:3671): Broken pipe (os error 32), waiting for SESSION_RESPONSE at <time> after 240 attempts; retrying in 30 s
```

A socket error names the handshake step it happened at. `bus` in `knx_project_summary` and `knx_bus_status` carries:

| Field | Meaning |
|---|---|
| `state`, `connected` | `connecting` (never connected yet), `connected` or `reconnecting` (also after a fatal stop). |
| `interface` | The gateway, as `192.0.2.10:3671` or `multicast 224.0.23.12:3671`. |
| `tunnel_user` | The KNXnet/IP Secure tunnelling user of the current or last connection; `null` on a plain tunnel. |
| `last_error`, `last_error_at` | The exact error of the last failed attempt or lost connection, and when (RFC3339). Kept as history after a reconnect. |
| `attempts` | Failed connect attempts since the bus was last connected; 0 while connected. |
| `retry_in_seconds` | Seconds until the next attempt, while waiting for one. |
| `connected_since` | When the current connection came up. |
| `stopped` | Only when the bus stopped for good on a connect error retrying cannot fix (a refused password, a secure-only interface without credentials), before it ever connected. Restart the server after fixing the cause. Once the bus has connected, the same errors are retried. |

**Tunnelling user choice.** With a key store that lists several tunnelling users for the interface, the tunnel takes, in order:

1. a user no other bussard process on this host holds,
2. a user whose tunnel slot the interface reports free,
3. the key store's order.

The user a tunnel holds is marked by a lock file `<dir>/.bussard/tunnel-users/<ip>-<port>-user<N>.lock` holding the process id; a lock whose process is gone is ignored and replaced. A user the interface refuses (a failed authentication, no free tunnel for it, or the connection closed or reset during the handshake) hands over to the next user in the same attempt, before the bus backs off. A timeout does not, since the next user would fare no better. The user chosen is logged at info level, a refused one at warning level. With `--secure-user` the named user is used and marked, without rotation.

**Two servers for one model.** Claude Desktop starts two `bussard mcp` processes for one configured entry. Each marks itself in `<dir>/.bussard/instances/` and logs a warning naming the other's process id at start; neither refuses to run. Each holds its own connection and, through the locks above, its own tunnelling user. `knx_bus_status` lists the other's process id in `other_instances`.

## The programming tier

`--allow-programming` lets the assistant finish a change instead of ending with "now type `bussard apply`". It exposes the single-device write of `bussard apply`, the link tables and the parameter octets that differ, written by the same code the CLI runs. It is off by default and never available with `--passive`.

!!! warning
    At this tier the assistant can write a device, after you say yes to its plan. Read the plan it shows you before you answer.

The gates, in front of every write:

- **Write gate.** A non-loopback gateway needs `BUSSARD_ALLOW_REAL_GATEWAY=1` or `--allow-remote-gateway`. The server refuses to start without it, and both tools check it again on every call.
- **Source-address probe.** Both tools refuse when a device already answers at the tunnel's own individual address, as the CLI device commands do. The server probes once per tunnel: a passed probe holds until the bus reconnects (`knx_bus_reconnect`, or a tunnel that re-establishes itself), and an occupied address refuses every call.
- **Plan digest.** `knx_plan_device` returns `plan_digest`, a SHA-256 over the device address, the model's links and parameter values for it, the desired tables, the parameter image the write would stream, what a secured write gives the security object (addresses, object numbers and sequence numbers, no key), and the live tables and parameter memory it read. `knx_apply_device` refuses unless the digest came from this server session within `--plan-ttl-minutes` (default 10) and a fresh read of the device, with the current model, reproduces it. A device changed by ETS or another tool, or an edited model, retires the digest. A digest is single use.
- **State hash.** The plan also carries `state_hash`, the same fingerprint `bussard plan --json` prints. `knx_apply_device` with `plan_hash` refuses when a fresh read no longer produces it. The digest stays required either way.
- **Human approval.** The tool descriptions tell the assistant to show the plan to the human and to call `knx_apply_device` only after an explicit yes in the conversation. The digest makes this checkable: an apply can only write what a plan showed.
- **Protected group addresses.** A plan whose additions or removals touch a `protected = true` group address is refused, with no override.
- **Identity.** A device whose application or mask drifted from `bussard.lock` is refused, naming the `bussard flash` it needs, as `bussard apply` refuses it.

An apply then runs exactly the CLI rails:

1. The pre-apply backups to `captures/backups/`: the tables, and the parameter memory when parameters change. No backup, no write.
2. A history snapshot `mcp knx_apply_device <address> <digest>` that names the gateway: the audit line `bussard history` shows.
3. The table write when a link changes, then the parameter-only download of the differing octets, each verified by reading back.

The result carries the verify outcome, what was written and the backup paths. One device per call.

**Parameters.** The plan reads the parameter memory on the same connection as the tables, with the product data `bussard.lock` pins, and lists every parameter that differs by key, vendor text, device value and model value, so the human approves them by name. The write uses the same [write set](commands/programming.md#parameter-only-download) as the CLI: only octets a parameter is placed in under the configuration, as ETS's download does. It refuses unless the device runs the application the product data describes. When the product data is missing (the lock pins an archive that is not in `products/`, or whose SHA-256 changed), `parameters.skipped` carries the recovery line, the plan says it writes the links only, and a links-only plan the human approved still applies.

**Device-managed parameters.** An `Access="None"` parameter the configuration reaches is owned by the application at runtime, for example a download flag. Its octets always differ from the model's image, so a plan whose only difference is such octets is `noop` and writes nothing. They are still written, at the model's value, alongside a table or parameter write, and listed in `octet_ranges` with the role `device_managed` (see [octet attribution roles](commands/programming.md#octet-attribution-roles)).

**A parameter that shows or hides a com-object** changes the group-object table, which a parameter download does not rewrite. The same `knx_plan_device` and `knx_apply_device` pair pushes it as a flash:

- The plan says `method: flash`, lists the com-objects that appear or disappear, the table sizes, the parameter backup and the pinned archive (`product_sha256`), and states that the device restarts and is offline for 30 to 50 s.
- Its question asks to flash the device, so the human's yes is a yes to the flash.
- The flash is the one `bussard flash <ia> --yes` writes, built by the same code from the same inputs.
- It is refused without an archive pinned in `bussard.lock`, for a device that carries another application or whose load state cannot be read, and on every gate above.
- The parameter memory is backed up to `captures/backups/parameters/` first, where `knx_restore_parameters` reads it.

**Secured devices.** A device the server's keyring lists is planned and written over KNX Data Secure, as `bussard apply --keyring` does. On System B the write also reprograms the security object. The gates above apply unchanged, and three more rules cover it:

- The plan shows what the security object receives (`security_object`: the secured senders, the keyed group addresses, the secured objects), so the human approves it with the tables. It names addresses and object numbers, never a key.
- A group the model marks `secure = true` without a group key in the keyring refuses the plan: a download without that key would leave the group unusable.
- The plan digest covers the security inputs. A keyring or `secure` flag that changes between plan and apply retires the plan.

A device the model records as `security.activated` but the keyring does not list is refused. System 7 devices get their tables written secured and their security object left as it is.

**KNX IP interfaces.** `knx_plan_device` and `knx_apply_device` write a `[knxnet]` table as `bussard apply` does (see [KNX IP interfaces](commands/programming.md#knx-ip-interfaces)), and refuse outright a change of the IP assignment, address or tunnel addresses of the interface the server tunnels through.

### The apply job

A client bridge may cut a tool call at 60 s, which a secured apply with a restart and a read-back exceeds. So `knx_apply_device` runs every gate, the snapshot and both backups inside the call, and the write as a job in the server:

- A refusal in the pre-flight is the call's reply; nothing was written and no job remains.
- After the pre-flight the call waits up to 20 s (from its start) for the write. If it ends, the reply is the full result (`started: false`, `done: true`). If not, the reply is `started: true` with the job id, and `knx_apply_status {job}` reports the step, the download progress and the final result.
- The pre-flight's device read is bounded too: past the 20 s read wait the call answers `started` while the pre-flight runs on, and a refusal after that ends the job with `result.refused: true`, nothing written. `knx_plan_device` runs its read the same way, as a plan job.
- One job per server at a time. A second `knx_apply_device`, or a `knx_plan_device`, while an apply runs is refused with the running job's id. The job holds the bus lock and the management slot until it ends.
- The job's record is `apply-result.json` in its history snapshot's directory (`.bussard/history/<snapshot>/`), written when the write starts and again when it ends. `knx_last_apply {address}` returns the latest job for a device, from the session or from that record, so a lost reply is recoverable after a server restart.
- A record left running by a stopped server reads as `interrupted`: plan again before trusting the device.
- The status tools never touch the bus.

The CLI `apply` is unchanged by this.

## The Home Assistant tier

`--allow-home-assistant` lets the assistant close the loop on the Home Assistant side. After a group address or a link changed, it shows what the KNX YAML Home Assistant reads would change and, after the human said yes, writes it and reloads the integration. It needs the flag and a `[home_assistant]` table in `bussard.toml` (see [`bussard.toml`](files/bussard-toml.md)); with only one of the two the tools are not registered. The tier never touches the KNX bus.

```toml
[home_assistant]
url = "http://homeassistant.local:8123"
token_env = "BUSSARD_HA_TOKEN"     # the default
config_path = "../ha/knx.yaml"     # relative to the model directory
```

!!! warning
    Every Home Assistant change needs an explicit yes. Reads (`knx_ha_status`, `knx_ha_plan`) are free.

- **The token** is a Home Assistant long-lived access token (profile page, Security). It is read only from the variable `token_env` names, exported or from the model's `.env` (a `.env` supplies `BUSSARD_*` names only). It is sent as a bearer header and appears in no result, error or log line. Keep it in an untracked `.env`. A long-lived token is an admin credential for Home Assistant: revoke it on the profile page when the laptop leaves.
- **Status.** `knx_ha_status` calls `GET /api/`, `/api/config`, `/api/config/config_entries/entry` and `/api/states`, and changes nothing. KNX entities created in Home Assistant's UI live in its `.storage` and are not visible through the REST API; bussard neither lists nor touches them.
- **One file, YAML-managed.** The only file written is `config_path`, and only when bussard recognises it: a package file with the single top-level key `knx:` (what `bussard ha-config` prints), or the inside of the block when `configuration.yaml` says `knx: !include knx.yaml` (every top-level key a KNX platform). The written file keeps that layout. A missing or empty file, a file with other top-level keys and a file that is not YAML get no digest; `file.reason` says what to do. For a new file: create it with `knx:` or `{}`, and include it from `configuration.yaml`.
- **Plan digest.** `knx_ha_plan` returns `plan_digest`, a SHA-256 over the file path, the layout, the text to write and the file's current bytes. `knx_ha_apply` refuses unless the digest came from this server session within `--plan-ttl-minutes` (default 10) and a new plan reproduces it, so an edit to the model, to `ha.toml` or to the file after the plan retires it. A digest is single use.
- **Human approval.** The tool descriptions tell the assistant to show the sentences to the human and to call `knx_ha_apply` only after an explicit yes in the conversation.
- **Write, then reload.** The apply checks that Home Assistant answers with the token, keeps the file's bytes under `<model dir>/captures/backups/ha/<unix seconds>.yaml`, writes the new text to a temporary file beside the target and renames it over the target, then calls `POST /api/services/knx/reload`, then reads the status again. A failed write reloads nothing. A failed reload is reported with the backup path, and the file stays written; restoring is copying the backup over the file and reloading.
- **No other change.** The tier calls `knx.reload` and `automation.reload` and no other service, and writes no other configuration.
- **Audit lines.** Each apply writes `audit: knx_ha_apply wrote <path> ...` on stderr.

### bussard-managed automations

Some logic the bus cannot do alone, such as "when Zu Hause (4/3/2) receives 1, switch guest mode (4/3/10) off". The assistant proposes it as a rule, and bussard writes it as a Home Assistant automation through the config API (`/api/config/automation/config/<id>`). The rule shape is deliberately small:

```json
{
  "id": "bussard_guest_mode_end",
  "alias": "Zu Hause beendet Gastmodus",
  "description": "Zu Hause ends guest mode",
  "when": { "ga": "4/3/2", "value": "1", "dpt": "1.001" },
  "then": [ { "send": { "ga": "4/3/10", "value": "0", "dpt": "1.001" } } ]
}
```

- `id` starts with `bussard_`, then lowercase letters, digits and underscores (64 characters at most). `alias` defaults to the rule's sentence. `description` is optional.
- `when.ga` triggers on an incoming GroupValueWrite. `when.value` (human form, as `knx_write_group` takes it) narrows it to one value; without it any value triggers.
- `then` lists one or more sends, run in order.
- Every address must be in `groups.toml`. `dpt` is optional when `groups.toml` types the address and refused when it contradicts it. A send to a `protected = true` address is refused.

Behaviour:

- bussard updates or removes an automation only when its id starts with `bussard_` and its description carries the line `managed by bussard (model <model dir name>)`. An automation made by hand, even under a `bussard_` id, is refused and never touched.
- `knx_ha_plan` lists the `bussard_` automations Home Assistant runs and flags addresses the model no longer has.
- `knx_ha_automation_plan` returns the automation and a `plan_digest`, a SHA-256 over the id, the config to write and the config Home Assistant stores now. `knx_ha_automation_apply` takes the digest after the human's yes, renders the rule again against the current model, reads Home Assistant again, and refuses when either moved.
- Before an update or removal, the previous automation's JSON is kept under `captures/backups/ha/automation-<id>-<unix seconds>.json`. Restoring is posting it back, or re-planning the old rule. Then bussard writes and calls `automation.reload`.
- `knx_ha_automation_remove` plans without a digest and deletes with one.
- The stderr audit lines are `audit: knx_ha_automation_apply wrote <id>` and `audit: knx_ha_automation_remove deleted <id>`.

??? note "Details"
    The rendering, for Home Assistant 2024.10 or later:

    - **Trigger:** the KNX integration's `knx.telegram` trigger on `when.ga`, incoming GroupValueWrite only.
    - **Value match:** a template condition on `trigger.payload` in the raw form the integration reports: an integer for a 1-, 2- or 4-bit DPT (`{{ trigger.payload == 1 }}`), a list of octets otherwise (`{{ trigger.payload | list == [255] }}`).
    - **Sends:** one `knx.send` action per send, with the raw payload bussard encodes from the value and DPT: an integer for a sub-byte DPT (`1.001` `0` becomes `0`), a list of octets otherwise (`5.001` `50%` becomes `[128]`). Home Assistant then needs no `type`.
    - **Mode:** `single`.
    - **Marker:** the description gets the line `managed by bussard (model <model dir name>)`.

## Argument errors and the server log

A tool call whose arguments do not fit comes back as a tool error that says what reached the server, followed by the fields the tool expects:

| Error text | What it means |
|---|---|
| "the call reached bussard without any arguments (the client sent none)" | The client or a bridge dropped the arguments: the request carried no `arguments` member. The fix is on the client side; retry with the arguments as a JSON object. |
| "with an empty object as its arguments" | The client sent `{}`. |
| anything else | serde's own text, with the path of the offending field, e.g. `com_object: invalid type: string "seven", expected u16`. |

The server logs every `tools/call` on stderr at info level (`-v`): the tool name, whether `arguments` was present, and the names of the fields received, never their values. A rejected call is also logged at warn level, so it shows without `-v`. With `-vv` the raw request is logged too, with every string value replaced by `<redacted>`.

Claude Desktop writes a server's stderr to `~/Library/Logs/Claude/mcp-server-<name>.log` on macOS, where `<name>` is the key in `mcpServers`. Claude Code shows it in the session's MCP output.
