# The model format

This is the contract for the files bussard reads and writes in the model
directory (`knx/` by default): which files exist, their shapes, how keys are
derived, and the errors bussard reports. The reasons behind the format are in
[DESIGN.md](DESIGN.md#52-the-model-files); the commands that read and write
these files are in [reference.md](reference.md).

## Files

```
knx/
  bussard.toml          connection and lint settings, hand-editable
  groups.toml           the group-address plan, hand-editable
  devices/1.1.47.toml   one file per device, hand-editable in full
  bussard.lock          @generated by import and adopt, never edited
  bussard.keys          KNX Secure key store, encrypted, written by `bussard keys`
  bussard.keys.bak      the previous key store, kept by every write
  tests.toml            optional bus tests, hand-editable
  ha.toml               optional Home Assistant overrides, hand-editable
  products/             the product archives the lock pins; retained, bussard never
                        regenerates it (committing it is your call, product-data.md)
  captures/             local only
  .bussard/history/     snapshots of the model files
  .bussard/facts/       @generated device facts per device, local only (reference.md)
  .bussard/models/      @generated product models, rebuilt from products/ when missing
```

A file is either fully user-owned or fully generated. Of the model files
(the ones snapshots, bundles and the fingerprint cover), `bussard.lock` is
the only generated one: `import`, `import-product` and `adopt` write it. The
generated files under `.bussard/` (device facts, product models) are
regenerable caches outside the model. Commit the lock, as you would
`Cargo.lock`. `bussard.keys` is written by `bussard keys` (and by `init` and
`import` when they find a keyring export), is encrypted, and is committed with
the model. A snapshot, a bundle and the model-change fingerprint cover
`bussard.toml`, `groups.toml`, `devices/*.toml`, `bussard.lock`, `tests.toml`
and `ha.toml`.

All files except `bussard.keys` (the ETS `.knxkeys` XML shape, see below)
are TOML 1.0 as written by bussard. The parser (the `toml` crate)
accepts TOML 1.1 input; the emitter never relies on it. Every string is a
basic string. Keys are bare wherever TOML allows it and quoted otherwise.
No key in a file bussard writes needs quotes except the parameter escape
hatch described below.

Files are written with `toml_edit`, so comments and the formatting of
untouched lines survive a save. Entries bussard adds or changes are
re-formatted; everything else stays byte-identical. An object key the model
no longer links is removed when the lock written by this save or the lock it
replaces resolves it; a key neither resolves was typed by hand and stays, so
validation reports it (E023). A re-import also puts sections and entries in
the order a fresh import writes them; comments move with their entries.

## `bussard.toml`

```toml
[connection]
transport = "tunnel"            # "tunnel" | "routing"
gateway = "192.168.1.74:3671"
# multicast = "224.0.23.12:3671"
# keyring = "house.knxkeys"   # deprecated: use the key store bussard.keys

[lint]
[lint.topology]
max_devices_per_line = 64
[lint.topology.supply_ma]
"1.1" = 640
[lint.groups]
scheme = "floor-trade-block"    # | "function-floor"
feedback_pairing = true
name_pattern = "* * *"
[lint.groups.blocks]
light = 5
blind = 10

[import]
# language = "de-DE"            # text language of import; see Text language
```

Written by `init`. bussard never rewrites it, except to append a `[lint]`
table when one is missing. `[lint]` configures the topology limits and the
group-address convention that `validate` checks. `[import]` is optional;
`language` overrides the language `import` derives texts and keys in.

## `groups.toml`

```toml
project = "Haus"

ranges = [
  { address = "0",   name = "UG" },
  { address = "0/0", name = "Beleuchtung schalten" },
  { address = "1",   name = "EG" },
]

groups = [
  { address = "0/0/1", name = "Licht Büro aussen Schalten", dpt = "1.001" },
  { address = "0/0/2", name = "Licht Büro aussen Status",   dpt = "1.001" },
  { address = "0/3/1", name = "Heizung Büro Soll",          dpt = "9.001", protected = true },
  { address = "1/2/3", name = "Jalousie Küche Auf/Ab",      dpt = "1.008", secure = true, description = "Süd" },
]
```

- `ranges` entries name a main group (`"3"`) or a middle group (`"3/2"`).
- `groups` entries carry `address`, `name`, optional `dpt`, `description`,
  `protected` (default false) and `secure` (default false).
- Order in the file is by address. The emitter pads the `name` column so the
  file reads as a table; a hand edit that breaks the alignment is fine.
- A duplicate `address` is validation error E020, reported on both lines.
- `dpt` must be a quoted string. A bare `1.001` is a float and is rejected
  with a fix-it hint (see Errors).
- The project file a model was imported from is recorded in the lock as
  `source`, not here.

## `devices/<address>.toml`

The file name is the individual address plus `.toml`. `address` inside the
file must match the file name (E002). The file is user-owned in full.

This is `devices/1.1.47.toml` from a real import (a Jung 2300.21 SU
switch/blind/input module), lightly trimmed:

```toml
address = "1.1.47"
name = "Switch actuator, 2-gang / blinds actuator, 1-gang"
description = "Fenster"
product = "230021SU"

[location]
floor = "DG"
room = "Kind 2 Süd"

[parameters]                            # device-level parameters (no channel)
regenalarm = "1"

[links]                                 # device-level objects (no channel)
regenalarm.listen = ["4/1/8"]

[channel.relaisausgaenge-1]             # handle from the lock; see Key derivation
bei-regenalarm = "schließen"            # parameter: scalar value
betriebsart = "Lüftungsklappe / Dachfenster"
langzeitbetrieb.listen = ["3/1/20"]     # object: table with send / listen / name
kurzzeitbetrieb.listen = ["3/1/21"]
rueckmeldung-lueftungsklappen-dachfensterposition.send = "3/1/23"
```

Product data has not activated this device's Data Secure capability, so it
carries no `[security]` table; `application` (an override) and `replaced`
are optional fields this device happens not to set. A parameter page
(`[channel.<handle>.<page>]`, one level down) exists only where the lock
defines one for that channel.

### Top level

| Key | Type | Notes |
|---|---|---|
| `address` | string | identity |
| `name` | string | required |
| `description` | string | optional |
| `product` | string | order number; optional but needed for anything beyond links |
| `application` | string | optional override of the program pinned in the lock |
| `replaced` | string | RFC 3339, set by `replace` |
| `[location]` | `floor`, `room` | optional |
| `[security]` | `activated`, `secure_commissioning` | intent only |
| `[parameters]` | table | device-level parameters |
| `[links]` | table | device-level objects |
| `[channel.<handle>]` | table | one per channel |

### Inside a channel table

Every entry other than `name` is classified by the shape of its value, then
checked against the lock:

- a string, integer or bool is a **parameter**;
- a table whose keys are a subset of `send`, `listen`, `name` is an
  **object**. `send` is the one GA the object transmits on (the object needs
  the T flag), `listen` the array of GAs it accepts writes from (the W
  flag), and `name` a user override of the object's display name;
- any other table is a **parameter page**, holding parameters one level
  down. Pages exist only where the lock defines them for that channel.

An object key is either the key the lock assigns (`langzeitbetrieb`) or the
bare object number (`144`). Both resolve to the same object; the emitter
writes the key from the lock when there is one.

A parameter key is the key the lock assigns. When the same text would
repeat within a scope, the lock assigns a longer key (page-qualified or
`<key>@<ref>`). The emitter writes whatever the lock says, and the reader
resolves through the lock.

The file holds only what ETS shows. ETS also stores values for parameter
refs the configuration does not show (an inactive branch, the alternative
of a shown ref) or that it never lets the user edit (`Access="None"`);
those are the lock's `hidden[]`, not the file's.

### Without product data

The readable keys come from the vendor's product data (`.knxprod`), not
from the ETS project. A device whose product data was never imported still
gets a device file, but its channel handles are the vendor's channel ids and
its objects are keyed by number. Parameters cannot be checked or flashed.
From the demo fixture:

```toml
address = "1.1.1"
name = "Push Button Hallway"
description = "4-fold push button with status LEDs"
product = "PB-4F"

[location]
floor = "Ground Floor"
room = "Hallway"

[links]
40.send = "3/1/0"
40.name = "Spare Output"

[channel.CH-1]
name = "Rocker 1 - Hallway Light"
0.send = "0/0/0"
0.name = "Hallway Light - Switch"
1.listen = ["0/0/1"]
1.name = "Hallway Light - Status LED"
```

Once the product data is available, `import` or `adopt` rewrites the lock
with keys, and the next save writes the readable form. The object numbers
stay valid as keys either way.

`[parameters]` and `[links]` at the top level follow the same rules for
objects and parameters that belong to no channel.

### Parameter values

The file stores the value the user means. The reader accepts:

- a string: an enum label (`"Jalousie"`), an enum code (`"2"`), a number
  with unit (`"21 °C"`, `"15 min"`), or free text for text parameters;
- an integer or a bool, which are converted to their string form.

A float is rejected with a fix-it hint, because `1.10` and `1.1` cannot be
told apart after parsing.

Normalization to the vendor code happens when the product model is
available (`.bussard/models/`): an enum label becomes its code, a number with unit is
checked against the range. Without the product model the string is kept as
written and validation reports that the value could not be checked.

`flash`, `plan`, `apply`, `reconstruct` and `replace` resolve an enum label
against the vendor program itself, read in the lock's `language` (see
[Text language](#text-language)). A label matches, in this order:

1. the member's text in the lock's language;
2. else its untranslated text (the program's `DefaultLanguage`);
3. else its text in any other language the program carries, so a file
   edited from an English catalogue still loads under a German lock.

The first step with a match decides. A label two members share at that step
is refused as ambiguous, and a label no member carries is refused with the
list of labels in the lock's language. `import-product` writes `.bussard/models/` in
the same language, so the MCP `knx_set_parameter` check accepts the labels
the device files carry.

The loader translates between the file key and the parameter ref through
the lock. A parameter key the lock does not list (a value the user sets for
the first time) resolves through the product model: the key must equal the
slug of exactly one parameter's text in the channel's scope (the module
definition's parameters for a module channel, the application's own
otherwise), that parameter must have exactly one ref in the model, and the
next save adds the key to the lock. A key that resolves neither way is
E023. A `<slug>@<ref>` escape key always resolves, lock or not; once the
lock names that parameter, the next save writes the lock's key instead. A key the
lock lists for one channel does not resolve in another channel's table.
A device whose lock entry is missing cannot resolve its parameters or
object keys; validation reports E021 with the command that creates the
entry (`adopt`, `import`, or `import-product` plus `import`).

The matching real lock entry, trimmed the same way:

```toml
version = 2
source = "home_test.knxproj"
language = "de-DE"

[[product]]
sha256 = "5e0c…"
file = "products/Jung_KNX_Aktoren.knxprod"
filename = "Jung_KNX_Aktoren.knxprod"
size = 1184233
origin = { kind = "index", order_number = "230021SU", url = "https://…" }
applications = ["M-0004_A-20DE-22-C7D8-O000A"]
order_numbers = ["230021SU", "230041SU"]

[[device]]
address = "1.1.47"
product = "230021SU"

product_sha256 = "5e0c…"

  { number = 144, key = "langzeitbetrieb", channel = "relaisausgaenge-1", function = "Langzeitbetrieb", dpt = "1.008", flags = "CWU",  ref = "MD-3_M-18_MI-1_O-2-0_R-38" },

  { key = "regenalarm",  ref = "P-19_R-38",                                     param = "P-19" },
  { key = "betriebsart", channel = "relaisausgaenge-1", ref = "MD-3_M-18_MI-1_P-14_R-14", param = "MD-3_P-14" },

  { ref = "MD-3_M-18_MI-1_P-103_R-160", value = "1" },

```

`hardware_ref`, `has_fdsk_certificate`, `sequence_number` and `module_bases`
are omitted here, not just trimmed: this device's application does not
resolve a distinct hardware ref, and Data Secure has not been activated on
it, so those fields (and `[security]` in the file above) are absent rather
than `false`/zero. `MD-3_M-18_MI-1_P-103_R-160` is a parameter whose
effective `Access` is `"None"`: ETS stores a value for it, but the
configuration never lets the user edit it, so it never gets a device-file
key at all, hidden or otherwise.

`language` is the language the lock's texts and keys were derived in (see
Text language). One `[[device]]` per device, sorted by address. The lock is
the join between the user's words and the vendor's ids:

- `[[product]]` records each product-data archive the model depends on,
  identified by `sha256`, its content hash. `file` is the archive's path
  under `products/` (absent only for an export whose program could not be
  extracted); `filename` and `size` describe it; `applications` lists the
  programs it carries and `order_numbers` the hardware its catalogue maps to
  one. `origin` says how to get it back: `{ kind = "index", order_number,
  url }` (downloaded through the pointer index), `{ kind = "file", path }` (a
  `.knxprod` given to `import-product` or `adopt`), or `{ kind = "knxproj",
  path, project_hash }` (a program `import` or `import-product` extracted
  once from an ETS export; `project_hash` is the export's hash). Every use
  verifies the file's `sha256` first. A save keeps every entry a device
  links and every entry that names an archive.
- `product_sha256` links a device to the `[[product]]` entry that carries
  its application. A device served both by an archive in the model and by
  an ETS export links the archive. A save links an unlinked device to an
  archive entry that lists its order number and application, and drops a
  link whose entry no longer lists the device's application.
- `application_id` is the `PID_PROGRAM_VERSION` the device must report, as
  ten hex digits (manufacturer, application number, version), and
  `application_version` the program's `ApplicationVersion`. Both follow from
  the application ref (`M-0004_A-20DE-22-…` is manufacturer `0004`,
  application `20DE`, version `0x22`); the lock writes them so a reader does
  not need the product data. `describe`, `plan`, `reconstruct` and `apply`
  compare them and `mask` with what the device reports: `describe` and
  `reconstruct` print an `identity` verdict (`match`, `drift` or
  `unmodelled`), `plan` warns on drift, and `apply` refuses a drifted device
  before any write, naming the `bussard flash` it needs. `audit` lists the
  devices whose stored facts drifted, the devices with no pinned product
  data, and pinned archives that are missing or whose content changed.
  `flash`, `apply`, `commission --flash` and `replace` refuse a pinned
  archive that is missing or whose hash is not the one the lock pins, before
  any bus access; `--product <FILE>` stays the explicit override.
- `channels[].key` is the handle used in `[channel.<key>]`. Without a
  `key`, the handle is `id`, the application's channel id (or module-instance
  channel id). `number` and `text` are the vendor's; `label_ref` is the
  parameter ref that carries the channel label (`TextParameterRefId`), when
  the vendor defines one; `base` is the module-instance base offset when the
  channel is a module instance.
- `module_bases` holds the base offsets of module instances that own no
  channel.
- `objects[]` lists every com-object the device has, whether linked or not.
  `key` is present when a key could be derived; `channel` names the channel
  handle; `text`, `function`, `dpt`, `size`, `flags`, `ref` and `secure` are
  the vendor's object definition.
- `parameters[]` lists the parameters the device file holds a value for,
  with the file key, channel, ref (the visible ref) and parameter id (the
  memory cell). Only one ref per parameter id appears. The channel label
  parameters are the channels' `label_ref`. The rest of the program's
  parameters, with their texts, types and defaults, are in the product model
  under `.bussard/models/`.
- `hidden[]` holds the values ETS stores for parameter refs the evaluated
  configuration does not show: refs in an inactive branch, the alternatives
  of a shown ref, and refs whose effective `Access` is `"None"` (ETS stores
  a value but never presents them as editable). The user never sees them in
  ETS, so they are generated data: a flash writes them as ETS would, the
  device file does not show them, and every import replaces them.
- The product facts (program, manufacturer, hardware, mask) and the device
  state of KNX Secure (`secure_capable`, `has_fdsk_certificate`,
  `sequence_number`, `secure_senders`) live here; the device file keeps only
  the intent.
- `secure_senders` is the security individual address table (PID 54) that
  `bussard adopt` read back from a Data Secure device, one
  `{ address = "1.1.5", sequence = 275149400526 }` row per sender the device
  accepts secured group telegrams from. A secured `flash` or `apply` writes
  these rows back next to the senders the model's links imply (a sender the
  links imply takes the derived sequence), so a device keeps accepting senders
  the model does not describe. An import never writes it. Not key material.

### Text language

Channel and object texts, parameter keys and enum labels come from the
vendor's program, which carries its texts in a `DefaultLanguage` plus
translation layers. `import` picks one language for all devices:

1. `[import] language` in `bussard.toml`, when set;
2. else the `language` the existing `bussard.lock` records, so a re-import
   keeps the keys it wrote;
3. else the language the ETS project states (`Language` or
   `DefaultLanguage` on `ProjectInformation`; the ETS 6 exports seen so far
   state none);
4. else the one language every program in the project offers, as default
   or translation. ETS exports the translations of the languages the
   project uses, so a German project's programs all carry de-DE even when
   their default is en-US. A language that is only every program's default
   gives way to a common translation; several candidates prefer en-US;
5. else the most common `DefaultLanguage`, else en-US.

A program without the chosen language keeps its untranslated texts. The
choice is recorded as the lock's `language`. Changing the override and
importing again rewrites the keys in the new language.

### Key derivation (done by import and adopt, recorded in the lock)

- **Channel handle:** a stem, then `-<n>`. The stem is the slug of the
  channel `Name` when that is a plain label: only letters (umlauts
  included), digits and spaces, at most 24 characters as a slug, and
  contained in the slug of the channel's text when there is one, as a whole
  `-`-separated word (`regler` is not contained in `raumtemperaturregler`, a
  longer word it happens to end with, but is in `heizung-regler`). Vendors
  that use `Name` for an internal id (`SMOD0_MotionDetector1_MP_CT_1`,
  `LICHTAUSGANG_1`, `W1 - TSM - Wippe 1`), for an untranslated word
  (`Manual operation` next to `Manuelle Bedienung`), or for a word the text
  merely ends with, fail that test, and the
  stem is then the slug of the channel's `Text` in the import language, with
  module arguments filled in and the label placeholder stripped (a
  placeholder's default text, as in `{{0: Eingang g+h}}`, stays). `n` is the
  channel `Number`, or for a module-instantiated channel the instance
  ordinal (1-based, in `M-<m>` order); it is not appended when the stem
  already ends with `-<n>`. A module channel whose text ends with a number
  after its arguments are filled in (`Ventilausgang 3`) takes that text as
  its handle, since the number is the instance's own. Without a stem the
  handle is `ch-<ordinal>`. Unique per device; a collision appends the
  ordinal.
- **Object key:** the shortest of these that is unique within the channel
  (or within the device-level scope): slug of `FunctionText`; slug of
  `Text` + `FunctionText`; either of those with `-<number>`. No key when the
  vendor gives no text at all; the file then uses the number.
- **Parameter key:** slug of the parameter `Text` (falling back to `Name`)
  when unique within its scope; else `<page slug>.<slug>` using the
  `ParameterBlock` text the ref sits in; else `<slug>@<ref>` as the escape
  hatch. Only a parameter the configuration shows *and* lets the user edit
  gets a key; the escape hatch is for such a parameter whose text still
  collides after page qualification, never for a hidden ref or one whose
  effective `Access` is `"None"` (see `hidden[]`); dropping it out of the
  key competition is what usually spares its same-named sibling the escape
  hatch. The channel's label parameter (`label_ref`) gets no key: its value
  is the channel `name`.
- **Slugs:** lowercase, `ä ö ü ß` to `ae oe ue ss`, everything not
  `[a-z0-9]` collapsed to `-`, trimmed; empty becomes `x`.

### Staleness

Validation compares each device file's `product` with the lock entry and
reports E022 when they differ or when the entry is missing, naming the
command to run. A lock entry for a device that has no file is dropped on
the next save. E032 (a warning) reports a `product_sha256` with no
`[[product]]` entry, and E033 (a warning) a `[[product]]` entry whose `file`
the model directory does not hold, with the command that gets it back.

### Lock version

bussard reads and writes lock version 2 only. A lock of another version is
refused with the fix: `bussard import <export> --dir <dir>` regenerates it.

## `bussard.keys`

The KNX Secure key store (issue #241), written by `bussard keys import` and
by `import`/`init` when a `.knxkeys` sits next to the project and
`BUSSARD_KEYRING_PASSWORD` is set. Every bus command reads its keys from it
unless `--keyring` or `BUSSARD_KEYRING` names an explicit file, and it wins
over the deprecated `connection.keyring`. It is git-tracked by
design: a checkout recovers the model and its keys together. `.bussard/`
never holds keys.

The file is the XML of an ETS `.knxkeys` export, protected the same way and
with the same password (`BUSSARD_KEYRING_PASSWORD`): every key and password
attribute is AES-128-CBC encrypted under the PBKDF2 keyring key, and the root
`Signature` covers every element and attribute, so a wrong password or a hand
edit fails the load. Do not edit it by hand.

```xml
<?xml version="1.0" encoding="utf-8"?>
<!-- bussard key store (issue #241). ... -->
<Keyring Signature="..." Project="House" CreatedBy="bussard 0.1.0" Created="2026-09-25T10:11:12" Format="bussard.keys/1" xmlns="https://github.com/tmbo/bussard/xml/keys/1">
  <Backbone MulticastAddress="224.0.23.12" Latency="1000" Key="..." />
  <Interface Type="Tunneling" Host="1.1.200" IndividualAddress="1.1.22" UserID="2" Password="..." Authentication="..." />
  <GroupAddresses>
    <Group Address="1/2/3" Key="..." />
  </GroupAddresses>
  <Devices>
    <Device IndividualAddress="1.1.12" ToolKey="..." SerialNumber="00FA12345678" FDSK="..." SequenceNumber="42" />
  </Devices>
</Keyring>
```

| Element | Holds |
|---|---|
| `Keyring` | `Project`, `Created` (fixed when the store is first written; it seeds the attribute IV), `CreatedBy`, `Format = "bussard.keys/1"`, `Signature`. |
| `Backbone` | The multicast (routing) key, address and latency. |
| `Interface` | A KNXnet/IP Secure tunnelling user or other interface: tunnel address, host, user id, session password, device authentication code, and the group addresses it may send to. |
| `GroupAddresses/Group` | One group key per group address, written three-level (`1/2/3`). |
| `Devices/Device` | Tool key, serial number, factory key (FDSK), management password and authentication code. `ToolKey` is optional: a device can be known by its factory key alone. `SequenceNumber` is the value the last ETS export recorded, carried through for the export and the security individual address table. |

What differs from an ETS export: the `Format` attribute and namespace, the
optional `ToolKey`, three-level group addresses, and stable ciphertexts. An
unchanged key or password keeps its encrypted bytes across writes (fixed
`Created`, keyed password prefixes), so `git diff` shows only the entries that
changed plus the signature line.

bussard's own Data Secure send sequences are not stored. They are seeded from
the clock (milliseconds since 2018-01-05), so a restored store never makes
bussard replay a sequence a device has already seen.

Every write goes through a temporary file and a rename, and keeps the
previous store as `bussard.keys.bak` until the next successful write. A write
that would produce the same bytes touches nothing.

## `tests.toml`

Optional acceptance tests for `bussard test`, run in file order. A test has
a stimulus (a bus `write` or a `manual` instruction for a human) and usually
an `expect`.

```toml
allow_protected = false

[[tests]]
name = "Kitchen ceiling light switches and reports"
write = { ga = "1/0/10", value = "on" }
expect = { ga = "1/0/12", value = "on", within = "2s" }

[[tests]]
name = "Wind alarm raises the blinds"
manual = "Trigger the wind alarm on the weather station"
expect = { ga = "3/1/0", value = "up", within = "5s" }
```

`within` defaults to 3 seconds. `allow_protected` is only half the gate for
tests that write a protected GA: `bussard test` also needs `--force`, and the
MCP tool refuses such a test outright.

## `ha.toml`

Optional overrides for `bussard ha-config`. Entities are an `[[entity]]`
array with an `address` field, in line with `groups.toml`; the address is the
entity's primary GA (the one Home Assistant sends to, or the state GA for a
sensor). Two entries for the same address are an error.

```toml
[global]
default_platform_for_switches = "switch"   # or "light"
exclude = [
  "0/0/1",   # a single GA
  "8/",      # every GA under main group 8
]

[[entity]]
address = "1/0/1"
platform = "light"
name = "Kitchen ceiling"
device_class = "outlet"

[[entity]]
address = "3/1/5"
merge = ["3/1/6"]    # extra listening GAs
```

[ha-config.md](ha-config.md) explains how the overrides combine with the
derivation.

## Errors

Parse errors keep the `toml` crate's caret and message and add a `help:`
line where the raw message misleads. The rules, matched on the message and
the text around the caret:

| Situation | help |
|---|---|
| `missing key for inline table element` after a line with an unbalanced `{` | the entry on line N is not closed; add `}` before the `,` |
| `missing comma between array elements` with an unclosed `[` above | the array `<name>` opened on line N is never closed; add `]` |
| `missing comma between key-value pairs` right after a `"` inside a string | escape the quote as `\"` or use a literal string `'…'` |
| `invalid literal string, expected '` right after `=` | `<key>` has no value; write `<key> = "…"` or remove it |
| `missing comma between array elements` with a `-` at the caret | TOML arrays have no `-` markers; remove the `-` |
| `string values must be quoted` with curly quotes at the caret | “ ” are not quotes in TOML; use straight `"…"` |
| `duplicate key` | secondary label `first defined here` on the earlier definition |
| `invalid type: floating point` into a string field | `<key>` must be a quoted string: `<key> = "<source text>"` |
| `invalid type: string "true", expected a boolean` | write `<key> = true` |
| `invalid type: string "…", expected a sequence` | write `<key> = ["…"]` |
| `invalid type: string "21", expected u16` | write `<key> = 21` |
| `unknown field` | `did you mean <closest>` by edit distance over the expected list |

Semantic errors are validation diagnostics in the existing E-code style,
with file, line and column from `toml_edit` spans:

| Code | Rule |
|---|---|
| E020 | duplicate GA in `groups.toml` (both lines), duplicate object in a device file |
| E021 | device has channels, parameters or keyed objects but no lock entry |
| E022 | device `product` differs from the lock entry |
| E023 | parameter or object key in a channel that neither the lock nor the product model resolves; lists the channel's keys |
| E032 | warning: a device's `product_sha256` has no `[[product]]` entry in the lock |
| E033 | warning: a `[[product]]` entry names a `file` the model directory does not hold |
| E024 | object linked to a GA whose main DPT number differs from the object's |
| E025 | `send` on an object without the T flag; `listen` on an object without the W flag |
| E026 | parameter values could not be checked because the product model is missing (warning) |

A GA mentioned in a device file that `groups.toml` does not define is a
warning during `validate` and is added to `groups.toml` by `import`,
`apply` and the MCP edit tools, named `<channel name> <object function>`
with the object's DPT, and reported as added.

## Earlier YAML models

Versions before the switch stored the model as YAML (`bussard.yaml`,
`groups.yaml`, `links.yaml`, `devices/*.yaml`). bussard does not read those
files. A directory that holds only them is refused with a message; re-import
the ETS project into an empty directory to get the TOML files. Product
models keep their YAML format; they now live under `.bussard/models/` and
regenerate from `products/`.
