# The model format

This is the contract for the files bussard reads and writes in the model
directory (`knx/` by default): which files exist, their shapes, how keys are
derived, and the errors bussard reports. The reasons behind the format are in
[DESIGN.md](DESIGN.md#52-the-model-files); the commands that read and write
these files are in [reference.md](reference.md).

## Files

```
knx/
  bussard.toml          connection and lint settings, hand-editable
  groups.toml           the group-address plan, hand-editable
  devices/1.1.47.toml   one file per device, hand-editable in full
  bussard.lock          @generated by import and adopt, never edited
  tests.toml            optional bus tests, hand-editable
  ha.toml               optional Home Assistant overrides, hand-editable
  models/               product models, local only (gitignored, unchanged format)
  vendor/               cached .knxprod files, local only
  captures/             local only
  .bussard/history/     snapshots of the model files
```

A file is either fully user-owned or fully generated. `bussard.lock` is the
only generated file: `import` and `adopt` write it and nothing else does.
Commit it, as you would `Cargo.lock`. A snapshot, a bundle and the model-change fingerprint cover
`bussard.toml`, `groups.toml`, `devices/*.toml`, `bussard.lock`, `tests.toml`
and `ha.toml`.

All files are TOML 1.0 as written by bussard. The parser (the `toml` crate)
accepts TOML 1.1 input; the emitter never relies on it. Every string is a
basic string. Keys are bare wherever TOML allows it and quoted otherwise.
No key in a file bussard writes needs quotes except the parameter escape
hatch described below.

Files are written with `toml_edit`, so comments and the formatting of
untouched lines survive a save. Entries bussard adds or changes are
re-formatted; everything else stays byte-identical.

## `bussard.toml`

```toml
[connection]
transport = "tunnel"            # "tunnel" | "routing"
gateway = "192.168.1.74:3671"
# multicast = "224.0.23.12:3671"
# keyring = "house.knxkeys"

[lint]
[lint.topology]
max_devices_per_line = 64
[lint.topology.supply_ma]
"1.1" = 640
[lint.groups]
scheme = "floor-trade-block"    # | "function-floor"
feedback_pairing = true
name_pattern = "* * *"
[lint.groups.blocks]
light = 5
blind = 10
```

Written by `init`. bussard never rewrites it, except to append a `[lint]`
table when one is missing. `[lint]` configures the topology limits and the
group-address convention that `validate` checks.

## `groups.toml`

```toml
project = "Haus"

ranges = [
  { address = "0",   name = "UG" },
  { address = "0/0", name = "Beleuchtung schalten" },
  { address = "1",   name = "EG" },
]

groups = [
  { address = "0/0/1", name = "Licht Büro aussen Schalten", dpt = "1.001" },
  { address = "0/0/2", name = "Licht Büro aussen Status",   dpt = "1.001" },
  { address = "0/3/1", name = "Heizung Büro Soll",          dpt = "9.001", protected = true },
  { address = "1/2/3", name = "Jalousie Küche Auf/Ab",      dpt = "1.008", secure = true, description = "Süd" },
]
```

- `ranges` entries name a main group (`"3"`) or a middle group (`"3/2"`).
- `groups` entries carry `address`, `name`, optional `dpt`, `description`,
  `protected` (default false) and `secure` (default false).
- Order in the file is by address. The emitter pads the `name` column so the
  file reads as a table; a hand edit that breaks the alignment is fine.
- A duplicate `address` is validation error E020, reported on both lines.
- `dpt` must be a quoted string. A bare `1.001` is a float and is rejected
  with a fix-it hint (see Errors).
- The project file a model was imported from is recorded in the lock as
  `source`, not here.

## `devices/<address>.toml`

The file name is the individual address plus `.toml`. `address` inside the
file must match the file name (E002). The file is user-owned in full.

```toml
address = "1.1.47"
name = "Jalousieaktor Kind 2"
description = "Fenster"
product = "230021SU"                    # order number, printed on the device
# application = "M-0004_A-20DE-22-C7D8-O000A"   # override only; normally pinned in the lock
# replaced = "2026-03-01T10:00:00Z"

[location]
floor = "DG"
room = "Kind 2 Süd"

[security]
activated = true                        # intent; device facts live in the lock
secure_commissioning = false

[parameters]                            # device-level parameters (no channel)
regenalarm = "Ja"

[links]                                 # device-level objects (no channel)
in-betrieb.send = "4/1/2"

[channel.a-1]                           # handle from the lock; see Key derivation
name = "Fenster Süd"                    # optional user label
betriebsart = "Jalousie"                # parameter: scalar value
zuordnung-regen = "Ja"
langzeitbetrieb.listen = ["0/1/3", "0/2/1"]   # object: table with send / listen / name
kurzzeitbetrieb.listen = ["0/1/5"]
status-position.send = "0/1/4"

[channel.a-1.sollwerte]                 # a parameter page, only when the lock says so
komfort = "21 °C"
```

### Top level

| Key | Type | Notes |
|---|---|---|
| `address` | string | identity |
| `name` | string | required |
| `description` | string | optional |
| `product` | string | order number; optional but needed for anything beyond links |
| `application` | string | optional override of the program pinned in the lock |
| `replaced` | string | RFC 3339, set by `replace` |
| `[location]` | `floor`, `room` | optional |
| `[security]` | `activated`, `secure_commissioning` | intent only |
| `[parameters]` | table | device-level parameters |
| `[links]` | table | device-level objects |
| `[channel.<handle>]` | table | one per channel |

### Inside a channel table

Every entry other than `name` is classified by the shape of its value, then
checked against the lock:

- a string, integer or bool is a **parameter**;
- a table whose keys are a subset of `send`, `listen`, `name` is an
  **object**. `send` is the one GA the object transmits on (the object needs
  the T flag), `listen` the array of GAs it accepts writes from (the W
  flag), and `name` a user override of the object's display name;
- any other table is a **parameter page**, holding parameters one level
  down. Pages exist only where the lock defines them for that channel.

An object key is either the key the lock assigns (`langzeitbetrieb`) or the
bare object number (`144`). Both resolve to the same object; the emitter
writes the key from the lock when there is one.

A parameter key is the key the lock assigns. When the same text would
repeat within a scope, the lock assigns a longer key (page-qualified or
`<key>@R-<ref>`). The emitter writes whatever the lock says, and the reader
resolves through the lock.

### Without product data

The readable keys come from the vendor's product data (`.knxprod`), not
from the ETS project. A device whose product data was never imported still
gets a device file, but its channel handles are the vendor's channel ids and
its objects are keyed by number. Parameters cannot be checked or flashed.
From the demo fixture:

```toml
address = "1.1.1"
name = "Push Button Hallway"
description = "4-fold push button with status LEDs"
product = "PB-4F"

[location]
floor = "Ground Floor"
room = "Hallway"

[links]
40.send = "3/1/0"
40.name = "Spare Output"

[channel.CH-1]
name = "Rocker 1 - Hallway Light"
0.send = "0/0/0"
0.name = "Hallway Light - Switch"
1.listen = ["0/0/1"]
1.name = "Hallway Light - Status LED"
```

Once the product data is available, `import` or `adopt` rewrites the lock
with keys, and the next save writes the readable form. The object numbers
stay valid as keys either way.

`[parameters]` and `[links]` at the top level follow the same rules for
objects and parameters that belong to no channel.

### Parameter values

The file stores the value the user means. The reader accepts:

- a string: an enum label (`"Jalousie"`), an enum code (`"2"`), a number
  with unit (`"21 °C"`, `"15 min"`), or free text for text parameters;
- an integer or a bool, which are converted to their string form.

A float is rejected with a fix-it hint, because `1.10` and `1.1` cannot be
told apart after parsing.

Normalization to the vendor code happens when the product model is
available (`models/`): an enum label becomes its code, a number with unit is
checked against the range. Without the product model the string is kept as
written and validation reports that the value could not be checked.

The loader translates between the file key and the parameter ref through
the lock. A device whose lock entry is missing cannot resolve its parameters
or object keys; validation reports E021 with the command that creates the
entry (`adopt`, `import`, or `import-product` plus `import`).

## `bussard.lock`

```toml
# This file is @generated by `bussard import` and `bussard adopt`. Do not edit it by hand.
version = 1
source = "home_test.knxproj"

[[device]]
address = "1.1.47"
product = "230021SU"
application = "M-0004_A-20DE-22-C7D8-O000A"
manufacturer = "Albrecht Jung"
manufacturer_ref = "M-0004"
hardware_ref = "M-0004_H-…"
mask = "07B0"
secure_capable = true
has_fdsk_certificate = true
sequence_number = 239362131378
channels = [
  { key = "a-1", id = "MD-3_M-18_MI-1_CH-25", number = 1, text = "Relaisausgänge 1/2", label_ref = "MD-3_M-18_MI-1_P-15_R-17", base = 2915 },
]
module_bases = { MD-1_M-48_MI-1 = 10476 }      # instances that own no channel
objects = [
  { number = 138, key = "in-betrieb",       text = "Allgemein", function = "In Betrieb",     dpt = "1.005", flags = "CRT",  ref = "O-138_R-13" },
  { number = 144, key = "langzeitbetrieb",  channel = "a-1", text = "Jalousie 1", function = "Langzeitbetrieb", dpt = "1.008", flags = "CWU", ref = "MD-3_M-18_MI-1_O-2-0_R-38" },
  { number = 162, key = "status-position",  channel = "a-1", dpt = "5.001", flags = "CRTU", ref = "MD-3_M-18_MI-1_O-2-18_R-11", secure = true },
]
parameters = [
  { key = "regenalarm",                     ref = "P-19_R-38",                 param = "P-19" },
  { key = "betriebsart",  channel = "a-1",  ref = "MD-3_M-18_MI-1_P-14_R-14",  param = "MD-3_P-14" },
  { key = "sollwerte.komfort", channel = "a-1", ref = "MD-3_M-18_MI-1_P-40_R-61", param = "MD-3_P-40" },
]
```

One `[[device]]` per device, sorted by address. The lock is the join between
the user's words and the vendor's ids:

- `channels[].key` is the handle used in `[channel.<key>]`. Without a
  `key`, the handle is `id`, the application's channel id (or module-instance
  channel id). `number` and `text` are the vendor's; `label_ref` is the
  parameter ref that carries the channel label (`TextParameterRefId`), when
  the vendor defines one; `base` is the module-instance base offset when the
  channel is a module instance.
- `module_bases` holds the base offsets of module instances that own no
  channel.
- `objects[]` lists every com-object the device has, whether linked or not.
  `key` is present when a key could be derived; `channel` names the channel
  handle; `text`, `function`, `dpt`, `size`, `flags`, `ref` and `secure` are
  the vendor's object definition.
- `parameters[]` lists every parameter that is stored or storable for this
  device with its file key, channel, ref (the visible ref) and parameter id
  (the memory cell). Only one ref per parameter id appears.
- The product facts (program, manufacturer, hardware, mask) and the device
  state of KNX Secure (`secure_capable`, `has_fdsk_certificate`,
  `sequence_number`) live here; the device file keeps only the intent.

### Key derivation (done by import and adopt, recorded in the lock)

- **Channel handle:** `<slug of channel Name>-<Number>` when the vendor gives
  a `Name` and a `Number`; for a module-instantiated channel the module's
  channel `Name` plus the instance ordinal (1-based, in `M-<m>` order);
  otherwise `ch-<ordinal>`. Unique per device; a collision appends the
  ordinal.
- **Object key:** the shortest of these that is unique within the channel
  (or within the device-level scope): slug of `FunctionText`; slug of
  `Text` + `FunctionText`; either of those with `-<number>`. No key when the
  vendor gives no text at all; the file then uses the number.
- **Parameter key:** slug of the parameter `Text` (falling back to `Name`)
  when unique within its scope; else `<page slug>.<slug>` using the
  `ParameterBlock` text the ref sits in; else `<slug>@R-<ref>` as the escape
  hatch. The channel's label parameter (`label_ref`) gets no key: its value
  is the channel `name`.
- **Slugs:** lowercase, `ä ö ü ß` to `ae oe ue ss`, everything not
  `[a-z0-9]` collapsed to `-`, trimmed; empty becomes `x`.

### Staleness

Validation compares each device file's `product` with the lock entry and
reports E022 when they differ or when the entry is missing, naming the
command to run. A lock entry for a device that has no file is dropped on
the next save.

## `tests.toml`

Optional acceptance tests for `bussard test`, run in file order. A test has
a stimulus (a bus `write` or a `manual` instruction for a human) and usually
an `expect`.

```toml
allow_protected = false

[[tests]]
name = "Kitchen ceiling light switches and reports"
write = { ga = "1/0/10", value = "on" }
expect = { ga = "1/0/12", value = "on", within = "2s" }

[[tests]]
name = "Wind alarm raises the blinds"
manual = "Trigger the wind alarm on the weather station"
expect = { ga = "3/1/0", value = "up", within = "5s" }
```

`within` defaults to 3 seconds. `allow_protected` is only half the gate for
tests that write a protected GA: `bussard test` also needs `--force`, and the
MCP tool refuses such a test outright.

## `ha.toml`

Optional overrides for `bussard ha-config`. Entities are an `[[entity]]`
array with an `address` field, in line with `groups.toml`; the address is the
entity's primary GA (the one Home Assistant sends to, or the state GA for a
sensor). Two entries for the same address are an error.

```toml
[global]
default_platform_for_switches = "switch"   # or "light"
exclude = [
  "0/0/1",   # a single GA
  "8/",      # every GA under main group 8
]

[[entity]]
address = "1/0/1"
platform = "light"
name = "Kitchen ceiling"
device_class = "outlet"

[[entity]]
address = "3/1/5"
merge = ["3/1/6"]    # extra listening GAs
```

[ha-config.md](ha-config.md) explains how the overrides combine with the
derivation.

## Errors

Parse errors keep the `toml` crate's caret and message and add a `help:`
line where the raw message misleads. The rules, matched on the message and
the text around the caret:

| Situation | help |
|---|---|
| `missing key for inline table element` after a line with an unbalanced `{` | the entry on line N is not closed; add `}` before the `,` |
| `missing comma between array elements` with an unclosed `[` above | the array `<name>` opened on line N is never closed; add `]` |
| `missing comma between key-value pairs` right after a `"` inside a string | escape the quote as `\"` or use a literal string `'…'` |
| `invalid literal string, expected '` right after `=` | `<key>` has no value; write `<key> = "…"` or remove it |
| `missing comma between array elements` with a `-` at the caret | TOML arrays have no `-` markers; remove the `-` |
| `string values must be quoted` with curly quotes at the caret | “ ” are not quotes in TOML; use straight `"…"` |
| `duplicate key` | secondary label `first defined here` on the earlier definition |
| `invalid type: floating point` into a string field | `<key>` must be a quoted string: `<key> = "<source text>"` |
| `invalid type: string "true", expected a boolean` | write `<key> = true` |
| `invalid type: string "…", expected a sequence` | write `<key> = ["…"]` |
| `invalid type: string "21", expected u16` | write `<key> = 21` |
| `unknown field` | `did you mean <closest>` by edit distance over the expected list |

Semantic errors are validation diagnostics in the existing E-code style,
with file, line and column from `toml_edit` spans:

| Code | Rule |
|---|---|
| E020 | duplicate GA in `groups.toml` (both lines), duplicate object in a device file |
| E021 | device has channels, parameters or keyed objects but no lock entry |
| E022 | device `product` differs from the lock entry |
| E023 | unknown parameter or object key in a channel; lists the channel's keys |
| E024 | object linked to a GA whose main DPT number differs from the object's |
| E025 | `send` on an object without the T flag; `listen` on an object without the W flag |
| E026 | parameter values could not be checked because the product model is missing (warning) |

A GA mentioned in a device file that `groups.toml` does not define is a
warning during `validate` and is added to `groups.toml` by `import`,
`apply` and the MCP edit tools, named `<channel name> <object function>`
with the object's DPT, and reported as added.

## Earlier YAML models

Versions before the switch stored the model as YAML (`bussard.yaml`,
`groups.yaml`, `links.yaml`, `devices/*.yaml`). bussard does not read those
files. A directory that holds only them is refused with a message; re-import
the ETS project into an empty directory to get the TOML files. Product
models under `models/` keep their YAML format and are unaffected.
